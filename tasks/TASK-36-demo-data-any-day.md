# TASK-36 — демо-стенд живёт в любой день окна

Заказчик открыл приложение в воскресенье и не увидел ни одной записи ни на одном рабочем
месте. Это не «выходной» — это одномерный слой данных: `state` считает дату один раз при
старте процесса и высевает записи ровно на неё. Проверяется одной командой:

```
curl "http://localhost:8099/api/schedule?date=<любая дата вне текущей недели>"   ->  slots: []
curl "http://localhost:8099/api/appointments?date=<любая дата кроме одной>"      ->  items: []
```

Задача TASK-34 «починила» это сдвигом точки отсчёта (`effectiveDate` = понедельник, если
сегодня воскресенье). Тесты позеленели, экран остался мёртвым: сдвинулась дата, а не
природа дефекта. Здесь чинится природа.

Внутри — три дефекта, которые нельзя разносить по задачам, потому что исправление любого
поодиночке даёт видимый, но нерабочий экран:

1. **Обед выдаётся за приём.** `buildSlots` и `isWithinPublishedShift` трактуют
   `kind: 'break'` наравне с `'work'`. У d-001 четверг — это `[{08:00–12:00, break}]`, и
   `GET /schedule/2026-08-13` отдаёт 16 свободных слотов в обед врача. Оператор запишет
   туда пациента, и сервер это подтвердит.
2. **Выходные захардкожены дважды и по-разному.** `data.js` размечает воскресенье как
   `off` с нулевым интервалом, `lifecycle.js` отдельно режет `dayIndex > 5`. Правка
   только в `data.js` даёт видимые слоты, бронь по которым отвечает 409 `outside_shift`.
3. **Публикация недели не создаёт записей.** `seedAppointments` вызывается ровно один
   раз. Успешная публикация ведёт на такой же пустой экран, и петля администратора
   недоказуема.

Плюс: `GET /schedule/мусор` отвечает 200 с пустым массивом. Три разных состояния — «не
опубликовано», «никто не работает», «дата битая» — сейчас неотличимы, и экран не может
объяснить человеку, что происходит.

## Готовность

1. Для **каждой** даты окна `[сегодня−2 … сегодня+7]`, где сегодня берётся из системных
   часов: `GET /schedule?date=d` отдаёт непустой набор слотов, `GET /appointments?date=d`
   отдаёт не меньше пяти записей. Условие сформулировано от системной даты намеренно:
   сдвигом точки отсчёта его не пройти, только данными.
1а. **Статусы правдоподобны для дня, а не одинаковы во всех днях.** Прошедшие дни —
   завершённые приёмы и неявки; сегодня — смесь, включая «на приёме»; будущие дни —
   только запланированные. Требовать все шесть статусов в каждом дне окна нельзя: тогда
   завтрашние приёмы окажутся завершёнными и попадут в кассу смены, и экран снова будет
   врать — на этот раз правдоподобно.
2. Интервал `kind: 'break'` не порождает слотов и не проходит валидацию брони. Тест:
   у врача с обеденным интервалом в этот день нет ни одного слота внутри обеда, а POST
   на время обеда возвращает 409.
3. Нерабочий день (`off`, `absent`, `block`) отклоняется в **одном** месте: `data.js` и
   `lifecycle.js` спрашивают один и тот же предикат, а не считают день по отдельности.
   Тест: для каждой даты окна множество времён из `GET /schedule` и множество времён,
   которые принимает POST, совпадают.
4. Публикация недели создаёт **слоты**, а не записи: после `POST /week-templates/publish`
   на неопубликованную неделю `GET /schedule?date=<рабочий день этой недели>` отдаёт
   непустой набор слотов, и все они свободны.

   **Записи туда не сеять.** Первая редакция требовала «после публикации
   `GET /appointments` непуст», и это противоречит и пункту 1, и смыслу публикации:
   посеянная запись делает слот занятым, то есть опубликованная неделя сразу выходит
   частично распроданной, а `admin-publish-week` ждёт ровно обратного — что у оператора
   появились свободные слоты. Демо-записи живут в окне из пункта 1; для недели за
   пределами окна пустой список записей — правильный ответ, и экран обязан сказать это
   словами, а не выглядеть сломанным.
5. `GET /schedule?date=мусор` и `GET /schedule/мусор` отвечают 400 с кодом ошибки, а не
   200 с пустым массивом.
