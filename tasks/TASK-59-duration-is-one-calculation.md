# TASK-59 — длительность считается одинаково на всех путях записи

Экран «Правила длительности» показывает «Первичный, категория „Приём“ → 60 мин | Включено».
Карточка записи оператора для той же первичной консультации показывает «Длительность по
правилам администратора: 30 мин». Заказчик, согласовывавший длительности, поймает это
за секунды.

Причина — одна строка: `slot-card.tsx:154` `useState<VisitType>('repeat')`. Тип приёма не
выводится ни из услуги, ни из истории пациента, и правило `dr-visit-repeat` (`set 30`)
заменяет базу целиком. Поэтому и «Первичная консультация» (норматив 30), и «Расширенный
приём» (норматив 60, 4500 ₽) дают одинаковые 30 минут.

Та же константа зашита в подсветку занятости: `operator-page.tsx:174-180` считает зону как
`resolveBookingDuration(filterService, 'repeat', …)` независимо от того, что выбрал
оператор, — поэтому сетка показывает «не влезет» не там, где надо.

Два других пути записи движок правил вообще не зовут: `waitlist.tsx:142-143`
`service?.duration ?? 30` и `patient-card-form.tsx:213` `svc?.duration ?? 30`.
`service-picker.tsx:99` печатает сырой норматив справочника, не пропущенный через правила.

Довесок из того же класса: запись из заявки листа ожидания теряет тип приёма и основание
оплаты — `createAppointment` уходит без `paymentType` и `visitType`, сервер молча ставит
`regular`, и пациент по ДМС приезжает к регистратору как платный.

## Готовность

1. **Тип приёма не подставляется умолчанием.** Пока оператор не выбрал тип, карточка
   считает длительность по базовому нормативу услуги; выбор типа пересчитывает её на
   экране. Тест: услуга с нормативом 30 показывает 30 до выбора и 60 после выбора
   «Первичный».
2. **Расширенный приём и первичная консультация дают разную длительность.** Тест
   сравнивает две услуги с разными нормативами и падает, если числа совпали.
3. **Подсветка занятости считается по выбранному типу приёма**, а не по константе.
   Тест: смена типа меняет число подсвеченных ячеек.
4. **Все пути записи проходят через один расчёт.** В `src` не остаётся выражений вида
   `?? 30` для длительности: запись из карточки слота, из заявки листа ожидания и из
   быстрой записи регистратора зовут `resolveBookingDuration`. Проверяется тестом,
   который создаёт запись каждым из трёх путей и сравнивает `end - start`.
5. **Справочник услуг показывает длительность после правил**, а не сырой норматив, либо
   явно подписывает её как норматив. Формулировку выбрать одну и применить в обоих местах.
6. **Запись из заявки не теряет основание оплаты и тип приёма.** Тест: заявка с ДМС →
   созданная запись имеет `paymentType: 'dms'`, и регистратор видит ДМС, а не «Обычный».
7. **Выключение правила меняет длительность реальной записи** — сценарий `admin-catalog`
   остаётся зелёным и после правки (регрессия на существующее поведение).
