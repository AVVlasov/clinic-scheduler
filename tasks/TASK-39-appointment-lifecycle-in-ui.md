# TASK-39 — жизненный цикл записи целиком в интерфейсе

Переходы разложили по рабочим местам по названию роли, а не по работе: врачу оставили
только терминальный переход, оператору — только создание и перенос. Сервер при этом умеет
больше, чем интерфейс показывает, и разрыв виден пользователю как тупик.

- **Отмены нет нигде.** По всему `src` единственная отправка статуса — `completed` в
  карточке врача. Сервер умеет и `cancelled`, и `DELETE` (последний вообще без клиента,
  при двенадцати тестах на него). В карточке слота две кнопки; в макете — «Отменить».
  Оператор не может освободить слот отказавшегося пациента.
- **Врач не может начать приём.** Элемента смены статуса в карточке визита нет ни
  одного, а кнопка «Завершить приём» гаснет, пока запись не в работе. Из восьми записей
  дня врач может закрыть две, и экран открывается сразу на заблокированной первой.
- **Из режима переноса нет выхода.** Выбранный слот сбрасывается только после успешной
  записи; передумать нельзя.

## Готовность

1. Оператор отменяет запись из карточки слота; слот становится свободным и снова
   продаётся. Проверяется запросом к серверу, а не состоянием экрана.
2. Из режима переноса есть выход, не создающий записи; после выхода выбор слота сброшен.
3. Врач ведёт запись по цепочке `scheduled → arrived → in_progress → completed`, не уходя
   с экрана. Экран открывается на записи, с которой можно работать, а не на первой по
   списку.
4. **Правило недоступного действия — одно на всю систему** (продублировать ссылкой в
   TASK-41 и TASK-49): недоступное действие остаётся видимым, рядом с ним причина
   недоступности обычным текстом, нажатие не отправляет запрос. Кнопок без причины и
   причин без кнопки не бывает.
   Тест: для каждого статуса записи в карточке есть хотя бы одно доступное действие ЛИБО
   явный текст, что делать дальше и кому.
   Первая редакция требовала «кнопку не показывать» — это тот же провал, что `disabled`
   с подписью «недоступна», только зеркальный: человек не узнаёт ни что действие есть,
   ни почему его нет. И три задачи волны давали три разных правила для одной ситуации.
4а. **Отмена сохраняется, а не стирается.** У отменённой записи хранятся причина отмены,
   время и инициатор; запись остаётся видимой в разборе, а не исчезает. Тест: после
   отмены запись доступна по идентификатору и несёт причину.
4б. **История переходов записи ведётся и видна** (ФТ 3.6.3 требует статусы «с историей
   изменений»; «Аудит изменений» — MUST HAVE). Тест: после отмены в журнале записи два
   перехода со временем и инициатором.
5. Сценарии `operator-reschedule` и `doctor-day-protocol` заведены, зелёные и переведены
   в `config/journeys.json` из `planned` в `required`.
