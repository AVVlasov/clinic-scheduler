# TASK-30 — завершённая запись неизменяема, идентификаторы не сталкиваются

Три находки приёмки прогона `g_20260808-192745` (**P1**) — все на сервере:

- **`PATCH` без `status` правит завершённую запись насквозь**: терминальность проверяется
  только при смене статуса, поэтому запрос без него свободно меняет врача, время, оплату и
  протокол закрытого визита. Клиентский запрет переноса (TASK-28) гонку не закрывает: если
  соседний АРМ завершит визит после того, как оператор загрузил экран, его устаревший
  `PATCH` всё равно перепишет закрытую медицинскую запись.
- **Счётчик идентификаторов остался на семи** ([data.js:287]), хотя демо-данные в
  понедельник и вторник создают восемь записей `a-001…a-008`. Первая новая запись в эти
  дни получает `a-008` повторно, и дальнейший поиск и `PATCH` по id меняют чужой визит.
- **`nextVisit=null` отвергается**: поле необязательное, клиент при пустом значении шлёт
  `null`, а `tryApplyProtocolPatch` принимает только строку и отвечает `400 invalid_field`.
  Врач, заполнивший обязательные жалобы и диагноз, не может завершить приём, пока не
  заполнит необязательное поле.

Первые два — дефекты, внесённые прошлым кругом исправлений; это нормальная цена правок, но
цена оплачивается только если их находят.

## Готовность

1. Любая правка записи в терминальном статусе отклоняется машинным кодом — независимо от
   того, есть ли в запросе `status`. Проверка живёт в общем модуле жизненного цикла.
2. Идентификатор новой записи гарантированно свободен при любом составе демо-данных:
   счётчик берётся из фактического состояния, а не из константы.
3. Пустое необязательное поле принимается как очистка (`null` допустим), обязательные —
   по-прежнему обязательны. Тест доказывает все три пункта, включая гонку: `PATCH` без
   `status` по записи, завершённой между чтением и записью, отклоняется.
