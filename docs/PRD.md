# PRD — clinic-scheduler

Составлен по материалам `ai/`: требования заказчика (`01-требования/`), оценка и бэклог
(`02-оценка/`), макеты рабочих мест и дизайн-система (`05-дизайн/`).

## Кто пользователь и что для него «работает»

| Роль | Смена выглядит так | «Работает» — это |
|---|---|---|
| **Оператор** колл-центра | 8 часов подряд ищет свободный слот и записывает по телефону | сетка расписания открылась, слот нашёлся и запись создалась быстрее, чем пациент повторит фамилию |
| **Регистратор** стойки | очередь у стойки: приход, оплата, талон | очередь смены видна одним экраном, приход и оплата отмечаются в два клика |
| **Врач** | день приёма, карточка визита, услуги | список приёмов на день, карточка текущего пациента и завершение приёма без ухода с экрана |
| **Администратор** площадки | шаблоны недели, справочник врачей, публикация расписания | шаблон недели применяется, расписание публикуется, карточка врача правится |

Общее для всех: интерфейс узнаётся как система СМ-Клиники (зелёный, Open Sans, скруглённые
основные кнопки) и держит плотность — воздух только между смысловыми группами.

## Границы MVP

**Входит.** Четыре рабочих места на данных стабов, по составу и разметке макетов из
`ai/05-дизайн/Clinic-scheduler UI макеты/`:

1. АРМ оператора: обзор смены, сетка ресурсов с шагом 15 минут, карточка выбранного слота,
   действия «записать» и «перенести».
2. АРМ регистратора: очередь смены с фильтрами, карточка визита, оплата и печать талона,
   отметка неявки.
3. АРМ врача: день приёма, карточка пациента, жалобы и диагноз, выполненные услуги,
   рекомендации, завершение приёма.
4. АРМ администратора: шаблоны приёма на неделю, публикация недели, справочник врачей с
   карточкой (все группы полей макета ARM-admin: специальности, площадки, кабинет,
   возраст пациента, лимит льготных, правила приёма, оборудование, работа в паре,
   доступность услуг во времени, теги специализации).

Плюс общий каркас: навигация между рабочими местами, тема дизайн-системы, клиент API и
express-стабы, отдающие правдоподобные данные (врачи, слоты, записи, пациенты, услуги).

## Источник правды по объёму

**`ai/01-требования/MVP_MAP.docx` — источник правды.** Решение владельца, 2026-08-09.

При расхождении между этим документом, макетами, сметой и настоящим PRD побеждает MVP MAP.
Основание для решения: сверка показала, что границы ниже были проведены по экранам макета,
а заказчик ведёт их по модулям, и три исключения прямо противоречили его колонке MUST HAVE.
Прежняя редакция PRD не ссылалась ни на один номер требования — именно поэтому расхождение
дожило до пятого круга приёмки.

Прослеживаемость «требование → сценарий → задача» — [TRACEABILITY.md](TRACEABILITY.md).
Строка без задачи там означает пробел, а не умолчание.

**Не входит в первую версию.** Каждое исключение — с основанием в документе заказчика:

- миграция с 1С, реверс-инжиниринг старой системы, перенос истории — требования нет ни в
  ФТ, ни в FAQ;
- транспорт уведомлений: шина, внешние потребители, провайдеры СМС, каскад
  Push → WhatsApp → СМС (FAQ: отдельный проект сервиса уведомлений). **Элементы АРМ из
  этого раздела входят в объём**: отметка «Запись подтверждена» и ручная отправка
  напоминания из карточки (ФТ 3.6.6);
- внешний каталог пользователей: LDAP и Keycloak, права и разрезы по площадкам (MVP MAP —
  вторая очередь). **Субъект входит в объём**: текущий сотрудник и подразделение нужны,
  чтобы выполнить ФТ 3.8.1 «отображать сотрудника, создавшего запись»;
- аттестация ИСПДн, СКЗИ, пентест (FAQ: шифрование обязательно для контура с реальными
  данными, аттестация не упоминается);
- база знаний — FAQ дословно: «Базу Знаний в целевом решении не используем»;
- автоматический оптимизатор маршрута — FAQ: «В MVP автоматический оптимизатор не
  закладываем». Возможность его добавить закладывается;
- корзина и множественная запись одной транзакцией, чек-листы и опросники по услуге —
  вторая очередь;
- долговременное хранение и глубина истории 2–3 года. Стабы держат данные в памяти
  процесса, но **журнал переходов записи входит в объём**: «Аудит изменений» — MUST HAVE.

**Вошло в объём по решению 2026-08-09** (прежде было исключено ошибочно):

- **лист ожидания** — MVP MAP: MUST HAVE, четыре типа заявок. Ручной режим; автоподбор
  остаётся второй очередью (FAQ: «автоматизированный подбор обсуждаемо с MVP»);
- **повторный визит и назначения** — MVP MAP: MUST HAVE, «История лечения». В объёме:
  рекомендация врача с датой и услугой порождает заявку, видимую оператору;
- **снос расписания**, **оборудование как ресурс**, **матрица компетенций**, **правила
  длительности**, **отсутствия и праздники диапазоном дат**, **печатные формы
  расписания**, **цветовая маркировка VIP / ДМС / первичный** — всё это стоит в колонке
  MUST HAVE карты MVP и оплачено по смете.

## Чем доказывается закрытая задача

Ни одно условие не закрывается осмотром. Минимум для любой задачи:

```
npx --no-install tsc --noEmit
npx --no-install eslint ./src --max-warnings=0
npm test
```

Сверх этого у каждой задачи есть собственные проверки в `config/checks.json` — команда,
проверяющая именно её поведение: маршрут стаба отвечает нужной схемой, компонент рендерит
строки очереди из данных, тема отдаёт токен нужного цвета. Тест обязан падать, если
реализацию убрать.

## Что осталось за человеком

Выборочная приёмка требований: автотест проверяет соответствие кода самому себе, а не
требованиям заказчика. Расхождение «агент понял требование по-своему → написал тесты из того
же понимания → гейт зелёный» ловится только чтением ФТ человеком. Подробности —
`ai/04-метод/Что_нельзя_отдать_агенту.md`.
