# clinic-scheduler

## Что это за продукт

Ядро расписания и записи для сети медицинских центров «СМ-Клиника»: четыре рабочих места —
оператор колл-центра, врач, регистратор стойки, администратор площадки. Границы MVP и то,
чем доказывается закрытие задачи, — в [docs/PRD.md](docs/PRD.md). Требования заказчика лежат
в `ai/01-требования/`, макеты — в `ai/05-дизайн/Clinic-scheduler UI макеты/`, дизайн-система —
в `ai/05-дизайн/smclinic-Design-System.md`.

## Стек и границы

- Языки/фреймворки: TypeScript, React 18, Chakra UI v3, react-router-dom v6, сборка `@brojs/cli`,
  бэкенд-стабы — Express (`stubs/api`), тесты — vitest + @testing-library/react.
- Явно НЕ используем: другие UI-киты и CSS-фреймворки (tailwind, MUI, bootstrap), redux и любые
  внешние стейт-менеджеры (хватает хуков и контекста), SSR, GraphQL, классовые компоненты.
- Новые зависимости: разрешены только devDependencies для тестов (например `supertest`) и то,
  что уже стоит в `package.json`. Новая runtime-зависимость — основание отклонить вариант.
- Данные только из стабов `stubs/api`. Никаких обращений к внешним системам, 1С и шине.

## Где что лежит

| Каталог | Что там |
|---------|---------|
| `src/pages/<арм>/` | экран рабочего места: компоненты, хуки и тесты рядом с кодом |
| `src/__data__/` | типы домена, клиент API, адреса навигации |
| `src/theme.tsx` | тема Chakra: токены дизайн-системы СМ-Клиники |
| `stubs/api/` | express-роутер стабов: маршруты и демо-данные |
| `ai/` | материалы заказчика: требования, оценка, макеты, дизайн-система |

Продуктовый код перечислен в `config/harness.json` → `productPaths`. Всё, чего там нет
(доки, скрипты, обвязка), правками по задаче не считается: харнесс не признаёт это
прогрессом.

## Как проверяется работа

Три команды. Красная любая — задача не закрыта:

```
npx --no-install tsc --noEmit
npx --no-install eslint ./src --max-warnings=0
npm test
```

Четвёртая — про продукт, а не про задачу:

```
pwsh harness/journey-gate.ps1
```

Она прогоняет сквозные сценарии из `config/journeys.json` — пути, ради которых продукт
существует. **Готовность продукта равна доле зелёных сценариев, а не доле закрытых
задач.** Первая волна закрыла 35 задач из 35 и не дала ни одного работающего пути:
каждый экран проверялся против мока собственного API, и граница «экран ↔ сервер» не
проверялась ничем. Все дефекты, которые увидел заказчик, оказались именно там.

- Быстрая проверка после каждой итерации: `config/harness.json` → `backpressure.typecheck`
- Раннер тестов: `config/harness.json` → `tests`
- Обязательные проверки задачи: `config/checks.json` под её id — их задаёт владелец, и
  сузить их агент не может.

Правило: **закрытая задача доказывается командой, а не осмотром.** «Работает» — не
условие готовности; «такая-то команда даёт такой-то результат» — условие.

## Источники правды и их старшинство

Решение владельца 2026-08-09. При расхождении побеждает тот, кто выше:

1. **`ai/01-требования/MVP_MAP.docx`** — объём: что входит в первую очередь, что нет.
2. `ai/01-требования/ФТ_118_требований.docx` и `FAQ_заказчика.docx` — поведение.
3. Макеты `ai/05-дизайн/Clinic-scheduler UI макеты/` — состав и разметка экрана.
4. `docs/PRD.md` — наш пересказ первых трёх. Расходится — правится он, а не они.

Покрытие требований — [docs/TRACEABILITY.md](docs/TRACEABILITY.md). Требование без задачи
там — пробел, а не умолчание. Спор об объёме разрешается ссылкой на строку документа, а не
мнением: пять кругов приёмки спорили о составе экрана заново, потому что ссылаться было
не на что.

## Правила, которые дороже всего нарушить

- **Макет — источник правды по составу и разметке экрана, дизайн-система — по цветам,
  шрифтам и плотности.** Токены берутся из `ai/05-дизайн/smclinic-Design-System.md`, а не
  подбираются на глаз. `#0D9B6C` и `#F07A35` — заливки; текст мельче 18px на них запрещён,
  для текста берутся `-700`-версии (`#0B6B4A`, `#9A4A10`).
- **Тест обязан падать без изменения кода.** Тест, зелёный и на пустой реализации, ничего не
  доказывает и считается отсутствующим.
- **Мокать можно всё, кроме границы, ради которой существует система.** `vi.mock` на
  `src/__data__/api` в тесте экрана — правильно: тест про экран. В сценарии из
  `src/journeys/` он **запрещён**: сценарий поднимает настоящие стабы
  (`src/journeys/journey-server.ts`) и проверяет эффект запросом к серверу. Двенадцать
  тестов АРМ начинались с мока API, и расхождение «сетка за одно число, записи за
  другое» было невоспроизводимо by construction.
- **Тест не читает системные часы.** Дата фиксируется (`vi.setSystemTime`) или передаётся
  параметром. Тест, зелёный шесть дней в неделю и красный на седьмой, обесценивает весь
  набор: красный прогон начинают объяснять словами «оно иногда падает».
- **Стабы отдают правдоподобные данные, а не заглушки.** Пустой массив вместо расписания
  превращает зелёный экран в ложь: проверить сетку на нём нечем.
- Моки и фейковые интеграции в продуктовом коде запрещены: экран, которому подложили
  данные, выглядит рабочим и проходит визуальную приёмку.
- **Русский язык в интерфейсе и в сообщениях об ошибках.** Идентификаторы, имена файлов и
  коммиты — латиницей.
- **Обвязку не трогаем.** `.claude/`, `config/`, `harness/`, `tasks/` кодовый агент не правит:
  это инструмент, которым его проверяют.
